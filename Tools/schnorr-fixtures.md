# Reproducing public BIP340 verification evidence

The Swift product verifies signatures. The optional C signer in this directory
exists only to generate deterministic, public test data for that verifier. It
does not become part of the Swift library, and no production key, wallet seed,
secret nonce or real funds are used. Never use these predictable values to
protect anything.

Run from the repository root with Git, Python 3 and Clang installed:

```sh
sh Tools/schnorr_reproduce.sh /absolute/path/to/new-scratch-directory
```

The destination must not exist. The script fetches the exact public revisions
below, compiles libsecp256k1 with its extrakeys and schnorrsig modules, generates
the fixtures, cross-checks every answer, then rewrites the JSON fixtures in this
repository. Regeneration is expected to be byte-identical. It changes no Swift
source. Ordinary Swift tests use checked-in fixtures and need neither network
access nor a C/Python toolchain.

The generator checks both source revisions and rejects tracked modifications.
For already available pinned checkouts, its direct invocation is:

```sh
python3 Tools/schnorr_generate_vectors.py /path/to/bips /path/to/secp256k1 /path/to/schnorr_oracle
python3 Tools/generate-public-point-vectors.py
```

## Pinned sources

- [BIP340 official vectors](https://github.com/bitcoin/bips/blob/927b6de9915c9262615a6399de51b200f81e5aa4/bip-0340/test-vectors.csv)
  and [Python reference](https://github.com/bitcoin/bips/blob/927b6de9915c9262615a6399de51b200f81e5aa4/bip-0340/reference.py):
  `927b6de9915c9262615a6399de51b200f81e5aa4`.
- [libsecp256k1 v0.7.1 source](https://github.com/bitcoin-core/secp256k1/tree/1a53f4961f337b4d166c25fce72ef0dc88806618):
  `1a53f4961f337b4d166c25fce72ef0dc88806618`.

`bip340-verification-official.json` preserves all 19 full signature-verification
decisions, including the four later arbitrary-message-length rows. Nine are
valid and ten invalid. Only public-key, message, signature, decision and comment
columns are retained. These decisions must not be confused with the separate
`xonly-validation.json` key-validity decisions: a bad signature can use a valid
key.

`bip340-verification-differential.json` contains 184 cases:

- 32 valid signatures generated by libsecp256k1 from public scalars, auxiliary
  values and messages derived with SHAKE256 and domain `winnow-public-bip340-v1`.
  The entire signature is compared byte-for-byte with the BIP340 Python signer.
- 128 mutations: one public-key, R-coordinate, s-scalar and message mutation
  per generated case. Both verifiers independently confirm rejection.
- Eleven canonical boundary cases, two explicitly constructed equations with
  `sG - eP` equal to infinity, and one with matching R.x but odd R.y.
- Ten malformed-length cases. These exercise adapter contracts; the C wrapper
  checks lengths before calling C, whose API takes fixed-size key/signature
  arrays. They are not tests of giving C an undersized memory allocation.

Every full-verification decision, official or generated, agrees with both the
pinned Python verifier and libsecp256k1. The 24 distinct message lengths range
from zero through 4,096 bytes and include SHA-256 block/padding boundaries.
This establishes differential agreement for these cases, not exhaustive
verification or proof of every implementation path.

## Independent point arithmetic

`generate-public-point-vectors.py` uses elementary affine formulas and Python
arbitrary-precision integers, with modular inversion through `pow(v, -1, p)`.
It does not import the Swift implementation or use its Jacobian formulas. The
resulting `public-point-vectors.json` contains 55 additions, 26 multiplications
and 25 inverses. Cases cover infinity, equal and opposite points, negative
points, scalar zero/one/order-minus-one, word boundaries, and deterministic
SHA-256-derived public scalars. Reference sanity checks independently verify
`nG` is infinity and `(n-1)G` is `-G`. Zero's inverse is represented as null.

Points are `{ "x": "64 hexadecimal digits", "y": "64 hexadecimal digits" }`;
infinity is JSON null. Scalars and field values are 32-byte big-endian hex.
The arithmetic fixture is another finite set of independent answers, not a
proof of the group implementation.

## Fixture identity

The verification tests assert the two signature-fixture hashes before decoding
them. Counts and source revisions are also recorded in
`bip340-verification-provenance.json`.

| Fixture | SHA-256 |
| --- | --- |
| `bip340-verification-official.json` | `c005451e8b883b2ca7a59ea2a7485027c7cb5f3312ee4a9a3c0c45a986126b01` |
| `bip340-verification-differential.json` | `6463d122bfa44e4e850ff371d724b10b157f0f129230312b8f5be0e2979433d8` |

Fresh-checkout reproduction completed successfully during development and
produced these same three hashes. That result is separate from the Swift
debug, release and device/simulator tests, whose results must be reported for
their actual tested revision.
