# Native Swift Bitcoin cryptography: capability and scope matrix

Research date: 2026-10-19. This is a source-inspection result and a proposed implementation boundary. It is not a wallet security audit or a claim that a replacement backend is ready.

Winnow needs more than Schnorr signing and verification to replace P256K. Its current code also uses secp256k1 public-key parsing, generator multiplication, point addition/multiplication/negation, public and private tweaks, and scalar arithmetic for MuSig2. The isolated first-pass experiment only parses and lifts public x-only keys; it does not yet satisfy that replacement surface.

**Frozen evidence.** The fresh Winnow clone is at `6566871db0a40be481dd63b7960790ef4de9192e`. Its [manifest](https://github.com/winnowwallet/winnow/blob/6566871db0a40be481dd63b7960790ef4de9192e/Package.swift#L16-L24) and [lockfile](https://github.com/winnowwallet/winnow/blob/6566871db0a40be481dd63b7960790ef4de9192e/Package.resolved#L4-L12) select P256K from swift-secp256k1 0.23.2, revision `e70a10e036a55fffea31568f0af92d69b6d449cd`. P256K [depends on its C libsecp256k1 target](https://github.com/21-DOT-DEV/swift-secp256k1/blob/e70a10e036a55fffea31568f0af92d69b6d449cd/Package.swift). Protocol references below are frozen at bitcoin/bips `927b6de9915c9262615a6399de51b200f81e5aa4`.

The source census covered `Sources/**/*.swift`, `Package.swift`, `Package.resolved`, and the development signet miner. Ten source files directly import P256K; every one is represented below. No `AGENTS.md` was present in the Winnow clone or the inspected ancestor directories. The user-supplied review preferences still apply. This pass did not request or claim a CRAP review, app coverage measurement, app build, or full app test run.

The ten direct-import files are `Vault.swift`, `BIP32.swift`, `BIP86.swift`, `TaggedHash.swift`, `MuSig.swift`, `MuSig2.swift`, `Taproot.swift`, `Descriptor.swift`, `PSBTRoles.swift`, and `Signer.swift`. This is a static source census, not a runtime trace or a transitive binary-size measurement.

**Specification checks.** [BIP340's lift_x and verification rules](https://github.com/bitcoin/bips/blob/927b6de9915c9262615a6399de51b200f81e5aa4/bip-0340.mediawiki#specification) define separate field modulus p and group order n. This experiment handles p only. [BIP32](https://github.com/bitcoin/bips/blob/927b6de9915c9262615a6399de51b200f81e5aa4/bip-0032.mediawiki#child-key-derivation-ckd-functions) requires private scalar addition and public point tweaks. [BIP341](https://github.com/bitcoin/bips/blob/927b6de9915c9262615a6399de51b200f81e5aa4/bip-0341.mediawiki#constructing-and-spending-taproot-outputs) requires the tweaked point and its parity. [BIP327](https://github.com/bitcoin/bips/blob/927b6de9915c9262615a6399de51b200f81e5aa4/bip-0327.mediawiki#algorithms) adds aggregation, nonce/session rules, scalar arithmetic and infinity-aware point operations. [BIP352's sending/receiving procedure](https://github.com/bitcoin/bips/blob/927b6de9915c9262615a6399de51b200f81e5aa4/bip-0352.mediawiki#sending) explicitly adds ECDH. These protocol requirements are distinct from measured experimental functionality.

**Proposed reusable boundary.** Keep field/scalar internals private and expose narrow typed x-only public keys first. Add compressed public points and a complete public BIP340 verifier only after their own vectors and independent differential tests. Bitcoin transaction serialization, sighashes, PSBT, BIP32 path policy and MuSig2 session orchestration can remain outside the arithmetic module. Existing CryptoKit hashes/HMAC and platform randomness should continue serving those roles. Future API shape and Swift Crypto placement require maintainer agreement; this inventory establishes no such agreement.

The successive gates remain: public verification, reviewed secret operations, app integration, signed device builds, then internal TestFlight. The first pass advances only a component of the public-verification gate. It changes no production wallet code and requires no signing or distribution credentials.
