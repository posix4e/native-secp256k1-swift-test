# Swift Crypto fit: a proposal, with unresolved policy constraints

Research date: 19 October 2026. Inspected `apple/swift-crypto` revision `0f6f68df04180034ef62e0d5f40195ac3189317a`. This is a source inspection and module proposal. No upstream contribution, contact, policy agreement, API agreement, size benchmark, or Swift Crypto build was performed.

A small, independently reusable package is a sensible research boundary. An upstream Swift Crypto home remains an open question. Its current policy requires new APIs to have a usable BoringSSL implementation; an independently implemented native Swift secp256k1 kernel does not by itself establish that requirement. Maintainers also require agreement in an issue before a pull request and ask contributors to write issue and PR discussions themselves. This document is an internal research note, not submission text. [Pinned contribution policy](https://github.com/apple/swift-crypto/blob/0f6f68df04180034ef62e0d5f40195ac3189317a/CONTRIBUTING.md#L59-L127).

The vendored BoringSSL named-curve API lists P-224, P-256, P-384, and P-521, without secp256k1. It also exposes an arbitrary-curve compatibility API with explicit cautions. Consequently, absence from the named-curve list should not be described as proof that every BoringSSL-based implementation is impossible. Whether a supported, maintainable BIP340 implementation can satisfy Swift Crypto's rule needs further investigation and maintainer judgment. [Named curves](https://github.com/apple/swift-crypto/blob/0f6f68df04180034ef62e0d5f40195ac3189317a/Sources/CCryptoBoringSSL/include/CCryptoBoringSSL_ec.h#L62-L92), [arbitrary-curve API](https://github.com/apple/swift-crypto/blob/0f6f68df04180034ef62e0d5f40195ac3189317a/Sources/CCryptoBoringSSL/include/CCryptoBoringSSL_ec.h#L335-L368).

Proposed boundaries for a later package design:

| Component | Responsibility | Exposure and dependencies |
|---|---|---|
| Native field/point kernel | Canonical field decoding, arithmetic, public-point parsing; later, reviewed group operations | Internal implementation. No wallet types or hash dependency. Variable-time public-data operations remain explicitly unsuitable for secrets. |
| Public verification product | A small API for validated x-only public keys and, after a separate milestone, BIP340 verification | Explicitly selected product; no signer or secret-key type initially. Keep the parser's error contract and encoded representation stable before broadening the API. |
| Hash adapter | BIP340 tagged SHA-256 using Apple CryptoKit; a future cross-platform adapter could use Swift Crypto's `Crypto` product | Reuse system hashing on Apple platforms. Do not implement another SHA-256 kernel. The present experiment already imports CryptoKit directly. |
| Bitcoin protocol layer | BIP32 derivation, Taproot tweaks, and MuSig2 sessions | Keep protocol state and wallet policies outside the arithmetic kernel. Add only through separate reviewed milestones. Silent Payments and ECDH remain outside today's minimum. |

These are proposed responsibilities, not targets implemented in this pass. A separate opt-in SwiftPM product could let consumers choose Bitcoin primitives without changing `Crypto`'s mainstream API. The product's eventual name, namespace, and repository placement would require agreement. Swift Crypto explicitly keeps most of its API aligned with CryptoKit and evaluates additional primitives selectively. [Pinned API evolution and primitive criteria](https://github.com/apple/swift-crypto/blob/0f6f68df04180034ef62e0d5f40195ac3189317a/README.md#L40-L72).

Dependency layout matters. At this revision, `Crypto` makes its BoringSSL and XKCP target dependencies conditional on non-Darwin platforms, and the SHA-256 source reexports CryptoKit when available. `CryptoExtras` unconditionally depends on `CCryptoBoringSSL` and `CryptoBoringWrapper`, plus `Crypto` and SwiftASN1. Putting a native kernel into today's `CryptoExtras` would therefore retain the BoringSSL dependency on Apple platforms. A claim that this placement removes C or shrinks an app binary would be unsupported. A new product or dependency restructuring would need separate review; nothing here measures linking, dead stripping, or installed binary size. [Pinned manifest](https://github.com/apple/swift-crypto/blob/0f6f68df04180034ef62e0d5f40195ac3189317a/Package.swift#L137-L166), [SHA-256 adapter behavior](https://github.com/apple/swift-crypto/blob/0f6f68df04180034ef62e0d5f40195ac3189317a/Sources/Crypto/Digests/HashFunctions_SHA2.swift#L15-L17).

For upstream readiness, preserve independently reproducible vectors and differential checks, document parsing and failure behavior, and eventually run the relevant complete algorithm-vector suites, including applicable Wycheproof cases. Those are stronger requirements than this bounded field-validation experiment. [Pinned testing requirements](https://github.com/apple/swift-crypto/blob/0f6f68df04180034ef62e0d5f40195ac3189317a/README.md#L62-L72).

The progression remains public verification → reviewed secret operations → app integration → signed device builds → internal TestFlight. Native arithmetic alone does not advance the secret-operation gate: scalar handling, timing, zeroization, nonce lifecycle, failure behavior, and appropriate platform randomness require their own design and evidence. No signing credentials, device distribution, maintainer contact, or publication is part of this first pass.
